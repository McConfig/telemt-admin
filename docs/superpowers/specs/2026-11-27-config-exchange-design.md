# Обмен конфигурацией и редактор прокси telemt

- Статус: на рассмотрении
- Дата: 2026-11-27
- Целевая версия: 2.0.0
- Подход: YAML-бандл `tgadmin.telemt/v1`, серверный precheck и apply,
  редактор telemt через Control API

## 1. Контекст

Сейчас настройки tgadmin меняются только через интерфейс и живут в Valkey.
Перенести их на другую установку, поделиться набором настроек с другим
администратором или сохранить снимок конфигурации перед экспериментами
нельзя. Раздел «Бэкапы» показывает только статус Valkey и хоста, но не
умеет выгружать и применять конфигурацию.

Отдельная проблема — конфигурация прокси telemt. Она лежит в
`telemt/config.toml` на хосте, содержит домен, режимы, порт, маскировку и
секреты клиентов. tgadmin управляет клиентами через Control API, но не
умеет читать и менять общие секции конфигурации. В результате «источник
правды» размазан между файлом, скриптом `telemt-init.sh` и панелью.

В telemt 3.5.17 есть Control API с ревизиями, валидацией и перезагрузкой:

- `GET /v1/config` — текущие редактируемые секции и ревизия;
- `GET /v1/config/schema` — схема путей, типов и правил применения;
- `POST /v1/config/validate` — проверка кандидата без записи;
- `PATCH /v1/config` — sparse-патч с `If-Match` и опциональной
  перезагрузкой;
- `POST /v1/system/reload` и `GET /v1/system/reload/{id}` — перезагрузка
  и статус.

Этого достаточно, чтобы tgadmin стал источником правды для конфигурации
прокси без монтирования файлов, без Docker-сокета и без перезапуска
контейнера telemt.

## 2. Цели

1. Экспортировать конфигурацию в один YAML-файл, удобный для чтения,
   diff и передачи другому администратору.
2. Экспортировать как полную установку, так и отдельные блоки:
   системные настройки, шаблоны лимитов, конфигурацию прокси,
   UI-пользователей, сервисные аккаунты, клиентов telemt.
3. Не включать секреты в файл по умолчанию; включать только по явному
   подтверждению паролем и вторым фактором.
4. Импортировать файл с предпросмотром: diff по блокам, список
   конфликтов, выбор «оставить как есть» или «переписать» для каждого
   имени, режим «слияние» или «замена» для блоков настроек и прокси.
5. Не применять ничего до подтверждения; при изменении целевой
   ревизии между precheck и apply блок не применять.
6. Дать редактор прокси в tgadmin: чтение, валидация, применение через
   Control API, история перезагрузок.
7. Вести аудит экспорта, импорта и изменений прокси, не записывая
   секреты.
8. Обеспечить идемпотентность импорта и понятный построчный отчёт.

## 3. Не входит в задачу

- Перенос TOTP-секретов и passkeys: TOTP зашифрован ключом конкретной
  установки, passkeys привязаны к RP ID и устройству.
- Экспорт паролей и токенов в открытом виде: в хранилище их нет.
- Редактирование `access.*` через редактор прокси: клиентами и политикой
  доступа управляет раздел «Клиенты» и `PATCH /v1/access/policy`.
- Изменение полей telemt, требующих перезапуска процесса
  (`server.port`, `server.api.enabled`, `server.api.listen`).
- Автоматический откат уже применённых блоков при ошибке в следующем.
- Импорт истории трафика, аудита, сессий и статистики.
- Шифрование файла паролем. Секреты защищаются только подтверждением
  при экспорте и обращением с файлом как с секретом.

## 4. Формат файла

### 4.1. Имя и версия

Имя по умолчанию:

```text
tgadmin-YYYYMMDD-HHMM.tgadmin.yaml
```

Расширение `.tgadmin.yaml`, MIME `application/yaml`.

Версия формата обязательна. Неизвестная версия — ошибка, а не частичный
импорт.

### 4.2. Каркас

```yaml
apiVersion: tgadmin.telemt/v1
kind: InstallationBundle
metadata:
  name: pantheon
  createdAt: "2026-11-27T14:00:00Z"
  appVersion: v2.0.0
  generator: tgadmin
  secrets: none
  sourceBaseUrl: https://tg.example.com
spec:
  settings: {}
  limitTemplates: []
  proxy: {}
  users: []
  services: []
  clients: []
```

Поля `metadata.sourceBaseUrl` и `metadata.appVersion` информационные, при
импорте не применяются. `metadata.name` используется для подтверждения
опасных операций.

`spec` содержит только выбранные блоки. Отсутствующий блок означает «не
экспортирован», а не «пустой».

### 4.3. Системные настройки

Настройки группируются по разделам каталога. Ключ поля — ключ определения
без префикса раздела; для полей без префикса (например, `retention`)
используется полный ключ:

```yaml
settings:
  risk:
    warn_ips: 3
    high_ips: 5
    distinct_7d: 4
    home_country: RU
    new_countries: true
  collect:
    interval: 30s
    retention: 720h
    session.ttl: 24h
  links:
    mode: tls
  quotas:
    reset_enabled: true
    reset_days: 30
    reset_time: "04:00"
  security:
    require_2fa: true
    password.min_length: 12
  interface:
    default_chart_days: 30
  logging:
    level: info
  notifications:
    events: "user.create,user.disable"
```

Правила:

- длительности — строки в формате Go (`30s`, `24h`, `720h`);
- перечисления — строки из допустимых значений;
- значения секретных полей при `secrets: none` отсутствуют;
- при `secrets: included` добавляются `notifications.webhook_url` и
  `notifications.webhook_secret`;
- раздел `infrastructure` не экспортируется как применяемый блок: он
  read-only и зависит от env. Допускается информационный блок
  `spec.infrastructureInfo` без импорта, но в 2.0.0 он не включается.

Для режима «замена» выбранного раздела недостающие в файле ключи
удаляются из overrides и начинают действовать значения по умолчанию или
из env. Для режима «слияние» меняются только ключи из файла.

### 4.4. Шаблоны лимитов

```yaml
limitTemplates:
  - name: default
    maxIps: 3
    maxTcpConns: 100
    dataQuotaBytes: 53687091200
    quotaPeriod: monthly
    rateLimitUpBps: 10000000
    rateLimitDownBps: 50000000
    expirationDays: 30
    sourceDeny:
      - 203.0.113.0/24
    riskWarnIps: 3
    riskHighIps: 5
    riskDistinct7d: 4
    riskNewCountries: true
    default: true
```

`default: true` переносит признак шаблона по умолчанию. Отсутствующие в
файле шаблоны удаляются только при включённой опасной опции
`deleteMissing` (см. 6.2).

### 4.5. Конфигурация прокси

```yaml
proxy:
  revision: "sha256:..."
  config:
    general:
      log_level: normal
      use_middle_proxy: true
    links:
      public_host: tools.q1w2e3.ru
      public_port: 8444
    modes:
      classic: false
      secure: false
      tls: true
    server:
      port: 8444
      metrics_listen: "10.0.0.9:3129"
      metrics_whitelist:
        - 10.0.0.9/32
    censorship:
      tls_domain: tools.q1w2e3.ru
      mask: true
      tls_emulation: false
```

`proxy.config` — JSON-совместимое подмножество `GET /v1/config`: объекты,
массивы, строки, числа, булевы значения. Секретов `access.*` там нет по
контракту telemt.

Какие секции отдаёт `GET /v1/config`: `general` (включая `general.links`
и `general.modes`), `timeouts`, `censorship`, `upstreams`, `dc_overrides`,
`web`, `network` (только `dns_overrides`) и `server` (только
`server.listeners` и пять observability-полей `server.api`). Порт,
bind-адреса, `auth_header` и `access.*` не отдаются и не редактируются.

`proxy.revision` — ревизия на момент экспорта. При импорте она не
используется как `If-Match`: на целевой установке ревизия другая. Она
нужна для диагностики и отображения «файл собран из другой версии
конфига».

При импорте:

1. Берутся только пути, у которых в `/v1/config/schema` есть
   `api.config_write: true`.
2. Поля с `api.config_write: false` и process-owned поля пропускаются с
   предупреждением.
3. Кандидат проверяется через `POST /v1/config/validate`.
4. Применение — `PATCH /v1/config` с `If-Match` текущей ревизии целевой
   установки и `reload=true`.
5. Если telemt вернул `202`, статус перезагрузки опрашивается через
   `GET /v1/system/reload/{id}`.

### 4.6. UI-пользователи

```yaml
users:
  - name: demo
    role: admin
    disabled: false
    totpEnabled: false
```

С секретами добавляется:

```yaml
    passwordHash: "$2a$12$..."
```

Правила:

- TOTP-секрет, резервные коды и passkeys не экспортируются;
- `totpEnabled: true` при импорте не восстанавливает TOTP, а даёт
  предупреждение «включите 2FA заново»;
- без секретов новый пользователь создаётся со случайным паролем,
  который показывается один раз в отчёте; существующий пользователь
  сохраняет пароль;
- с секретами новый пользователь получает bcrypt-хеш из файла;
- нельзя перезаписать пароль текущего администратора: precheck это
  блокирует;
- нельзя понизить или отключить последнего активного администратора:
  precheck это блокирует.

### 4.7. Сервисные аккаунты

```yaml
services:
  - name: monitoring
    scope: read
    tokens:
      - id: "0123456789abcdef"
        label: prometheus
        createdBy: demo
        createdAt: "2026-11-20T10:00:00Z"
        expiresAt: "2027-01-01T00:00:00Z"
        secretHash: "sha256:..."
```

Без секретов блок `tokens` отсутствует, сервисный аккаунт создаётся без
токенов. С секретами переносятся хеши; существующие токены продолжают
работать. Токены с уже существующим `id` не перезаписываются.

### 4.8. Клиенты telemt

```yaml
clients:
  - username: main
    enabled: true
    maxTcpConns: 100
    maxUniqueIps: 3
    expirationRFC3339: "2027-01-01T00:00:00Z"
    dataQuotaBytes: 53687091200
    quotaPeriod: monthly
    rateLimitUpBps: 10000000
    rateLimitDownBps: 50000000
    sourceDeny:
      - 203.0.113.0/24
    note: "рабочий ноутбук"
    trusted:
      countries: [GE, TR]
      ips: [192.0.2.50]
    risk:
      warnIps: 3
      highIps: 5
      distinct7d: 4
      newCountries: true
```

С секретами добавляется `secret: "0123456789abcdef0123456789abcdef"` —
ровно 32 hex-символа.

Правила:

- без секретов новый клиент создаётся с секретом, сгенерированным telemt;
  в отчёте один раз показываются ссылки;
- с секретами используется секрет из файла, в том числе при перезаписи
  существующего клиента через `PATCH /v1/users/{name}`;
- при перезаписи поля, отсутствующие в файле, не меняются (merge
  patch);
- заметки, доверенные страны и адреса, риск-переопределения хранятся в
  tgadmin и восстанавливаются отдельно от telemt.

## 5. Экспорт

### 5.1. Пресеты

В интерфейсе три пресета:

| Пресет | Блоки |
|---|---|
| Только настройки | settings, limitTemplates |
| Без клиентов | settings, limitTemplates, proxy, users, services |
| Полная выгрузка | settings, limitTemplates, proxy, users, services, clients |

Любой блок можно снять или добавить вручную.

### 5.2. Секреты

- по умолчанию `secrets: none`;
- включение секретов требует текущий пароль и, если у пользователя
  включён TOTP, действующий код;
- при экспорте секретов сервер проверяет пароль и код заново, даже если
  сессия активна;
- в ответе `Cache-Control: no-store`, `Content-Disposition: attachment`;
- факт экспорта с секретами пишется в аудит без значений.

### 5.3. Порядок сборки

1. Проверить права: только администратор, только cookie-сессия.
2. Проверить выбранные блоки и доступность telemt.
3. Собрать `spec` в фиксированном порядке.
4. Сериализовать YAML с отступом 2 и завершающим переводом строки.
5. Проверить, что в результате нет полей, помеченных секретными, если
   `secrets: none`.
6. Отдать файл.

## 6. Импорт

### 6.1. Шаг 1: precheck

`POST /api/config/precheck` принимает YAML до 4 МиБ. Ничего не меняет.

Проверки:

- размер, кодировка UTF-8, строгий YAML без дублирующихся ключей;
- `apiVersion` и `kind`;
- обязательные поля `metadata` и выбранных блоков;
- настройки — существующими валидаторами `settings.Validate`;
- шаблоны — `settings.ValidateTemplate`;
- прокси — `POST /v1/config/validate` для отфильтрованного кандидата;
- пользователи — имя, роль, формат bcrypt-хеша, защита последнего
  администратора и текущего пользователя;
- сервисы — имя, scope, формат хешей токенов;
- клиенты — имя, лимиты, формат секрета, доступность telemt;
- проверка секретов: если в файле есть секретные поля, требуется пароль
  и TOTP-код, иначе блок с секретами не принимается.

Результат:

```json
{
  "planId": "…",
  "expiresAt": "2026-11-27T14:15:00Z",
  "file": { "name": "tgadmin-20261127-1400.tgadmin.yaml", "sha256": "…" },
  "blocks": [
    {
      "id": "settings",
      "title": "Системные настройки",
      "available": true,
      "mode": "merge",
      "changes": 12,
      "warnings": []
    }
  ],
  "diff": {
    "settings": [
      { "path": "risk.warn_ips", "before": 3, "after": 4 }
    ],
    "proxy": [
      { "path": "censorship.tls_domain", "before": "old.example", "after": "new.example" }
    ]
  },
  "conflicts": {
    "users": [
      { "name": "demo", "action": "keep", "changes": ["role", "disabled"] }
    ],
    "services": [],
    "clients": [
      { "name": "main", "action": "keep", "changes": ["maxUniqueIps"] }
    ]
  },
  "deletions": {
    "limitTemplates": ["old-template"],
    "users": [],
    "services": [],
    "clients": []
  }
}
```

План хранится в Valkey 15 минут:

- ключ `config:plan:<id>`;
- привязка к имени пользователя и ID сессии;
- хеш файла и разобранный план;
- целевые ревизии Valkey и telemt;
- одноразовое использование.

### 6.2. Шаг 2: apply

`POST /api/config/apply`:

```json
{
  "planId": "…",
  "blocks": ["settings", "limitTemplates", "proxy"],
  "modes": { "settings": "merge", "proxy": "replace" },
  "conflicts": {
    "users": { "demo": "overwrite" },
    "services": {},
    "clients": { "main": "overwrite" }
  },
  "deleteMissing": false,
  "confirmName": "pantheon"
}
```

Правила:

- применяются только блоки, перечисленные в `blocks`;
- `settings` и `proxy` поддерживают `merge` и `replace`;
- `limitTemplates`, `users`, `services`, `clients` работают в режиме
  «создать отсутствующих, существующих по выбору»;
- `deleteMissing` — отдельная опасная опция, по умолчанию `false`. Она
  удаляет шаблоны, пользователей, сервисы и клиентов, которых нет в
  файле, но не меняет поведение существующих: для них по-прежнему
  действует выбор «оставить как есть» или «переписать». Включение
  требует `confirmName`, равный `metadata.name` из файла, и показывает
  список удаляемых в precheck;
- удаление текущего администратора и последнего администратора
  запрещено;
- удаление клиентов и сервисов показывается в precheck отдельным
  списком;
- если ревизия Valkey или telemt изменилась после precheck, блок
  возвращает `stale_plan`, остальные блоки не применяются;
- план помечается использованным до начала применения, повторный apply
  возвращает `plan_used`;
- каждый блок применяется отдельно; результат:

```json
{
  "results": [
    { "block": "settings", "status": "applied", "changed": 12 },
    { "block": "limitTemplates", "status": "applied", "created": 1, "updated": 2 },
    { "block": "users", "status": "applied", "created": 1, "updated": 0, "skipped": 2 },
    { "block": "proxy", "status": "failed", "error": "telemt: field_not_editable", "details": ["server.port"] }
  ]
}
```

При ошибке блока следующие блоки не применяются, уже применённые
остаются. Повторный импорт с новым precheck идемпотентен.

### 6.3. Порядок применения

1. settings;
2. limitTemplates;
3. users;
4. services;
5. clients;
6. proxy.

Прокси применяется последним, потому что перезагрузка telemt влияет на
клиентов и сбор.

### 6.4. Секреты при импорте

- файл с `metadata.secrets: included` требует пароль и TOTP-код;
- без подтверждения precheck возвращает `secrets_confirmation_required`;
- секреты не попадают в diff: показывается только факт «секрет будет
  изменён»;
- в отчёте новые пароли и ссылки клиентов показываются один раз и не
  сохраняются в аудите.

## 7. Редактор прокси

### 7.1. Данные

- `GET /v1/config/schema` кэшируется на 5 минут;
- `GET /v1/config` читается при открытии вкладки и после применения;
- в форме показываются пути с `api.config_write: true`;
- пути с `api.config_write: false` и process-owned поля показываются в
  блоке «Только через файл» с причиной из схемы;
- для массивов и map используется JSON-редактор с валидацией по схеме;
- для enum — выпадающий список, для bool — переключатель, для чисел —
  поле с min/max.

### 7.2. Применение

1. Пользователь меняет поля, нажимает «Проверить».
2. Сервер собирает sparse-патч только из изменённых путей и вызывает
   `POST /v1/config/validate`.
3. При успехе показывается список изменённых путей и предупреждения
   `apply.reload` / `apply.effect`.
4. «Применить» вызывает `PATCH /v1/config?reload=true` с `If-Match`.
5. `200` — применено; `202` — перезагрузка выполняется, интерфейс
   опрашивает `GET /v1/system/reload/{id}`;
6. `409 revision_conflict` или `runtime_conflict` — сообщение
   «конфигурация изменилась, обновите страницу», без retry;
7. опасные пути (`censorship.tls_domain`, `general.modes.*`,
   `server.listeners`, `links.public_host`, `links.public_port`)
   требуют подтверждения со списком изменений.

### 7.3. Ограничения

- порт, bind-адреса, `server.api.enabled`, `server.api.listen`,
  `auth_header` и `access.*` не отдаются API и не редактируются; для
  них показывается пояснение «только через файл или перезапуск»;
- `access.*` не показывается: клиентами управляет раздел «Клиенты»;
- редактор не пишет файл напрямую и не перезапускает контейнер;
- если Control API недоступен, вкладка показывает ошибку и кнопку
  «Повторить», остальные настройки работают.

## 8. API

Все маршруты — под `withAPISession`, только администратор, CSRF для
не-GET.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/config/export/blocks` | список блоков и пресетов |
| POST | `/api/config/export` | собрать YAML, тело: blocks, secrets, password, code |
| POST | `/api/config/precheck` | разобрать YAML и вернуть план |
| POST | `/api/config/apply` | применить план |
| GET | `/api/config/plan/{id}` | получить план повторно в пределах TTL |
| GET | `/api/proxy/schema` | схема telemt с кэшем |
| GET | `/api/proxy/config` | текущий конфиг и ревизия |
| POST | `/api/proxy/validate` | проверить патч |
| POST | `/api/proxy/apply` | применить патч и перезагрузить |
| GET | `/api/proxy/reload/{id}` | статус перезагрузки |

Ошибки:

| Код | HTTP | Когда |
|---|---|---|
| `bad_yaml` | 400 | синтаксис, дубли ключей, неизвестные поля |
| `unsupported_version` | 400 | другая `apiVersion` |
| `too_large` | 413 | файл больше 4 МиБ |
| `secrets_confirmation_required` | 403 | нужен пароль или TOTP |
| `bad_credentials` | 403 | неверный пароль или код |
| `plan_not_found` | 404 | план истёк или чужой |
| `plan_used` | 409 | повторное применение |
| `stale_plan` | 409 | изменились настройки или конфиг telemt |
| `proxy_unavailable` | 503 | Control API недоступен |
| `proxy_conflict` | 409 | `revision_conflict` или `runtime_conflict` |
| `forbidden` | 403 | не администратор или сервисный токен |

## 9. Безопасность

- экспорт и импорт — только администратор и cookie-сессия; сервисный
  токен получает `403 session_required`;
- повторная аутентификация для секретов: пароль + TOTP-код, если TOTP
  включён; passkey-подтверждение не используется в v1;
- CSRF и проверка Origin — существующим middleware;
- лимит частоты: 10 экспортов и 5 precheck/apply в минуту на
  пользователя;
- YAML-парсер строгий, без алиасов и якорей (защита от bomb);
- секреты не пишутся в логи, аудит, ошибки и diff;
- ответы с секретами — `Cache-Control: no-store`;
- план привязан к сессии и пользователю, TTL 15 минут, одноразовый;
- импорт не может удалить последнего администратора или самого себя;
- импорт не применяет `metadata.sourceBaseUrl`, env-зависимые и
  process-owned поля;
- все изменяющие действия — в аудите: `config.export`,
  `config.import.precheck`, `config.import.apply`, `proxy.update`,
  `proxy.reload`.

## 10. Интерфейс

### 10.1. Вкладка «Бэкапы»

Две карточки над существующим статусом бэкапов.

Экспорт:

- чекбоксы блоков;
- пресеты;
- переключатель «Включить секреты»;
- при включении — поля пароля и TOTP-кода;
- кнопка «Скачать YAML»;
- подпись с предупреждением, что файл с секретами нельзя передавать
  третьим лицам.

Импорт:

- drag-and-drop файла или вставка текста;
- кнопка «Проверить»;
- после precheck — карточки блоков с diff, режимом и предупреждениями;
- конфликты по именам с переключателем «оставить» / «переписать»;
- опция «удалить отсутствующих» только в режиме замены, с вводом имени
  установки;
- кнопка «Применить выбранное»;
- отчёт по блокам, новые пароли и ссылки — один раз, с кнопкой
  «Скопировать».

### 10.2. Вкладка «Прокси»

- статус подключения к Control API и текущая ревизия;
- форма по секциям с поиском;
- кнопки «Проверить» и «Применить»;
- панель diff перед применением;
- блок «Только через файл»;
- последние пять перезагрузок со статусом.

### 10.3. Доступность

- все поля с подписями и aria-label;
- ошибки текстом, не только цветом;
- таблицы конфликтов и diff доступны с клавиатуры;
- на узких экранах блоки перестраиваются в одну колонку.

## 11. Хранение и совместимость

- новых таблиц нет, кроме временных ключей плана
  `config:plan:<id>` с TTL;
- ключи формата не меняются;
- версия формата `tgadmin.telemt/v1` фиксируется в спеке и коде;
- при добавлении полей в v1 допускается только обратная совместимость:
  новые необязательные поля, старые не удаляются;
- несовместимые изменения — `tgadmin.telemt/v2` с явным отказом
  импортировать v2 в старую версию;
- откат tgadmin на версию ниже 2.0.0 безопасен: новые ключи плана
  игнорируются, настройки и конфиг telemt остаются рабочими.

## 12. Тестирование

### 12.1. Go

- golden-тесты экспорта для каждого пресета;
- проверка, что при `secrets: none` нет секретных полей;
- строгий парсер: дубли ключей, неизвестные поля, чужая версия,
  огромный файл, YAML-бомба;
- merge и replace для настроек;
- diff и конфликты для пользователей, сервисов, клиентов;
- защита последнего администратора и текущего пользователя;
- precheck без side effects;
- apply: план одноразовый, TTL, чужая сессия, `stale_plan`;
- идемпотентность повторного импорта;
- фильтрация process-owned полей прокси;
- ошибки telemt: `field_not_editable`, `revision_conflict`,
  `runtime_conflict`, `reload_in_progress`;
- аудит без секретов.

### 12.2. API

- таблица маршрутов и прав: admin, viewer, service token;
- CSRF и Origin;
- rate limit;
- `413` на большой файл;
- `403` на секреты без подтверждения;
- `409` при изменении ревизии между precheck и apply.

### 12.3. Frontend

- диалог экспорта: пресеты, блоки, секреты, валидация пароля;
- precheck: diff, конфликты, переключение «оставить/переписать»;
- опасная опция удаления;
- отчёт и одноразовые секреты;
- форма прокси: типы, read-only, поиск, diff, ошибки;
- состояния загрузки и пустые состояния.

### 12.4. E2E

`fake-telemt` дополняется:

- `GET /v1/config`;
- `GET /v1/config/schema`;
- `POST /v1/config/validate`;
- `PATCH /v1/config` с `If-Match` и `reload`;
- `GET /v1/system/reload/{id}`;
- ошибками `revision_conflict`, `field_not_editable`.

Сценарии:

1. Экспорт «Только настройки» без секретов, импорт в чистый стенд,
   проверка значений.
2. Экспорт полной выгрузки без секретов, precheck, импорт, новые ссылки
   клиентов.
3. Конфликт по имени, выбор «оставить», повтор с «переписать».
4. Редактор прокси: изменить домен, проверить, применить, увидеть
   новую ревизию.
5. Отказ при устаревшей ревизии.
6. Экспорт с секретами: пароль и TOTP, файл содержит хеши, импорт
   восстанавливает доступ.

## 14. Риски и меры

| Риск | Мера |
|---|---|
| Секреты утекают в файл или лог | белый список полей, проверка перед сериализацией, `no-store`, аудит без значений |
| Импорт ломает вход | защита текущего и последнего администратора, подтверждение паролем, precheck |
| Импорт прокси роняет прокси | только валидируемые API-поля, `validate`, `If-Match`, подтверждение опасных путей |
| Расхождение ревизий | план хранит ревизии, apply отказывает `stale_plan` |
| Частичное применение | порядок блоков, построчный отчёт, идемпотентный повтор |
| Несовместимость версий telemt | фильтрация по схеме, понятная ошибка, fake-telemt в e2e |
| Большой файл или YAML-бомба | лимит 4 МиБ, строгий парсер без алиасов |
| Потеря комментариев `config.toml` | документировано: источник правды — API, шаблон остаётся справочным |

## 15. Открытые вопросы

1. Нужен ли информационный блок `infrastructureInfo` в YAML для
   диагностики (без импорта)?
2. Нужна ли кнопка «Скачать текущий конфиг telemt как TOML» в редакторе
   прокси для ручного сравнения с файлом?
3. Нужен ли экспорт в JSON для автоматизации, или YAML достаточно?

Ответы по умолчанию: да для 1, да для 2, нет для 3.

## 16. Критерии готовности

1. Все шесть блоков экспортируются и импортируются по спеке.
2. Секреты не попадают в файл без подтверждения; тест это проверяет.
3. Precheck не меняет состояние и даёт diff и конфликты.
4. Apply идемпотентен, отказывает при устаревшей ревизии и не удаляет
   лишнего без явного подтверждения.
5. Редактор прокси читает схему, валидирует, применяет и показывает
   статус перезагрузки.
6. `go test ./...`, frontend coverage, e2e и CI зелёные.
7. Документация, ADR, скриншоты и CHANGELOG обновлены.
8. Рабочий хост обновлён до v2.0.0 и здоров.
