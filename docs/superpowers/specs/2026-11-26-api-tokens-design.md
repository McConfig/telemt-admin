# API-токены и сервисные аккаунты

- Статус: принято
- Дата: 2026-11-26
- Целевая версия: 1.9.0
- Подход: единый principal в существующем middleware плюс отдельные
  сервисные аккаунты

## 1. Контекст

API TeleMT Admin сейчас принимает только cookie-сессию пользователя UI.
Скрипты автоматизации, мониторинг и внешние интеграции вынуждены хранить
пароль администратора, поддерживать сессию и CSRF-токен. Это даёт им
полный доступ человека, не позволяет ограничить права и усложняет
ротацию: смена пароля завершает все сессии, а отозвать доступ скрипта
отдельно нельзя.

Проект уже умеет ограничивать доступ по `TGADMIN_ALLOWED_CIDRS`, хранит
пользователей, сессии и аудит в Valkey и различает роли `admin` и
`viewer`. Нужен машинный способ аутентификации, который использует ту же
инфраструктуру, но не зависит от пароля, сессии и CSRF.

## 2. Цели

1. Дать внешним скриптам доступ по `Authorization: Bearer` без пароля и
   cookie.
2. Ограничить права тремя уровнями: `read`, `write`, `admin`.
3. Отделить машинные учётки от людей: сервисные аккаунты не входят в UI и
   не имеют пароля.
4. Показывать полный токен ровно один раз и хранить только хеш секрета.
5. Поддержать несколько токенов на сервис для ротации без простоя.
6. Поддержать срок жизни и бессрочные токены, отзыв и отключение сервиса.
7. Вести аудит создания, изменения, удаления сервисов и выпуска/отзыва
   токенов.
8. Не менять существующие контракты API и модель cookie-сессий.

## 3. Не входит в задачу

- отдельные права на каждую конечную точку или ресурс;
- токены, привязанные к человеку, и управление чужими токенами из
  «Пользователей UI»;
- OAuth2, JWT, внешние identity provider, mTLS;
- ограничение токена по IP или подсети сверх общего allowlist;
- аудит каждого запроса по токену;
- веб-интерфейс для просмотра журнала использования токенов;
- автоматическая ротация токенов по расписанию;
- ограничение скорости запросов по токену.

## 4. Архитектура

### 4.1. Единый principal

Cookie-сессия и Bearer-токен приводятся к одному объекту в контексте
запроса:

```go
type Principal struct {
    Name    string // пользователь UI или имя сервиса
    Kind    string // session или service
    Role    store.Role
    Scope   string // пусто для сессии; read, write или admin
    TokenID string // пусто для сессии
}
```

- Для cookie-сессии `Kind=session`, `Role` берётся из пользователя UI,
  `Scope` пуст.
- Для Bearer-токена `Kind=service`, `Name` — имя сервиса, `Role`
  вычисляется из scope: `read` → `viewer`, `write` и `admin` → `admin`.
- `Scope` хранится отдельно, потому что `write` даёт административные
  права только на пути `/api/users*`, а не на весь API.

`withAPISession` сначала проверяет наличие `Authorization: Bearer`. Если
заголовок есть, cookie игнорируется. Если заголовка нет, работает
прежняя cookie-сессия. Обе ветки кладут principal в контекст, а для
сессии дополнительно сохраняется объект сессии для CSRF.

`apiCSRF` пропускает запросы с `Kind=service`: браузер не подставляет
Bearer автоматически, поэтому CSRF и проверка Origin не нужны.
`currentSession` для сервисного запроса возвращает `nil`; аудит и
`apiMe` используют principal.

### 4.2. Проверка прав

`isAdmin(r)`:

- сессия — роль пользователя UI;
- сервис `admin` — `true`;
- сервис `write` — `true` только для пути, начинающегося с `/api/users`;
- сервис `read` — `false`.

Этого достаточно, потому что все административные операции с клиентами
живут под `/api/users*`, а настройки, администраторы, аудит, диагностика
и сервисные аккаунты — вне этого префикса. Для `write` проверка пути
явная, а не через префикс в каждом обработчике.

Управление сервисными аккаунтами и токенами требует
`Kind=session` и роль `admin`. Токен не может выпустить новый токен,
создать сервис или изменить их права. Это ограничивает расширение
доступа при утечке токена.

Сервисные токены не допускаются к эндпоинтам, привязанным к cookie-сессии:
`/api/account/*`, `/api/sessions`, смена пароля и TOTP. Для сервиса они
возвращают `403 session_required`. Поэтому middleware проверяет не только
роль, но и явный список разрешённых префиксов путей: `/api/users*`,
`/api/summary`, `/api/me`, `/api/logout`, а для scope `admin` ещё
`/api/settings*`, `/api/admins*`, `/api/audit`, `/api/audit.csv`,
`/api/diagnostics`. Всё остальное для сервиса закрыто.

2FA-ограничение применяется только к cookie-сессии. Сервисный аккаунт не
проходит TOTP: он создаётся администратором из интерфейса, где
требование 2FA уже действует. Если требование 2FA включат позже, уже
выпущенные токены продолжают работать; это осознанное решение, потому
что машинный токен нельзя перевести на TOTP.

Allowlist `TGADMIN_ALLOWED_CIDRS` применяется до аутентификации и
действует одинаково для сессий и токенов.

### 4.3. Аутентификация по токену

Формат:

```text
tgadm_<16 hex id>_<43 base64url secret>
```

Разбор:

1. Проверить регулярное выражение формата.
2. Загрузить `auth:token:<id>`.
3. Проверить, что сервис существует и не отключён.
4. Проверить `expires_at`, если он задан.
5. Сравнить SHA-256 секрета с сохранённым хешем за постоянное время.
6. Обновить `last_used_at`, если прошло больше 60 секунд.

Любая ошибка возвращает `401 invalid_token` с сообщением «неверный или
истёкший токен». Разные причины не раскрываются, чтобы не давать оракул
для перебора.

При успехе principal получает
имя сервиса в виде `service:<name>`, scope сервиса и ID токена. Аудит
пишет actor `service:<name>`, чтобы события сервиса не смешивались с
событиями человека с тем же именем. `GET /api/me` для сервиса возвращает
его имя, роль и scope; `POST /api/logout` для сервиса отвечает `204` без
действия.

## 5. Модель данных

### 5.1. Ключи Valkey

| Ключ | Тип | Назначение |
|---|---|---|
| `auth:services` | set | имена всех сервисных аккаунтов |
| `auth:service:<name>` | hash | описание, scope, disabled, даты, автор |
| `auth:service_tokens:<name>` | set | ID токенов сервиса |
| `auth:token:<id>` | hash | сервис, метка, хеш секрета, срок, last_used |

Поля `auth:service:<name>`:

- `description` — до 200 символов, может быть пустым;
- `scope` — `read`, `write` или `admin`;
- `disabled` — `true` или `false`;
- `created_at`, `updated_at` — RFC3339 UTC;
- `created_by` — имя администратора UI.

Поля `auth:token:<id>`:

- `service` — имя сервиса;
- `label` — до 64 символов, может быть пустым;
- `secret_hash` — hex SHA-256 секрета;
- `created_at` — RFC3339 UTC;
- `created_by` — имя администратора UI;
- `expires_at` — RFC3339 UTC или пусто для бессрочного;
- `last_used_at` — RFC3339 UTC, обновляется не чаще раза в минуту.

Для срочного токена ключу ставится TTL до `expires_at`. Ссылка в
множестве `auth:service_tokens` может остаться после истечения TTL;
список токенов удаляет осиротевшие ID.

### 5.2. Ограничения

- Имя сервиса: `^[a-z0-9][a-z0-9_.-]{0,31}$`.
- Описание: до 200 символов после trim.
- Метка токена: до 64 символов после trim.
- Scope: только `read`, `write`, `admin`.
- Срок: `0` (бессрочно) или от 1 до 3650 дней. Если поле
  `expiresInDays` не передано, используется 90 дней; явный `0` означает
  бессрочный токен.
- Не больше 50 сервисных аккаунтов.
- Не больше 20 активных токенов на сервис. Перед проверкой лимита и
  выдачей списка осиротевшие и истёкшие ID удаляются из множества.
- Имя сервиса уникально; удаление освобождает имя.
- Существующие токены наследуют новый scope сразу после изменения
  сервиса. Это явно показывается в интерфейсе.

### 5.3. Жизненный цикл

Создание сервиса:

1. Проверить имя, описание и scope.
2. `HSETNX auth:service:<name>`.
3. Добавить имя в `auth:services`.
4. Записать аудит `service.create`.

Изменение:

1. Проверить поля.
2. Обновить hash и `updated_at`.
3. Записать аудит `service.update` со старым и новым scope/disabled.

Отключение:

- `disabled=true` блокирует все токены сервиса без удаления.
- Повторное включение возвращает доступ к прежним токенам.

Удаление:

1. Проверить тело `{"confirm":"<name>"}`.
2. Удалить все ключи токенов из `auth:service_tokens`.
3. Удалить hash сервиса, имя из множества, множество токенов.
4. Записать аудит `service.delete`.

Выпуск токена:

1. Проверить лимит 20.
2. Сгенерировать 8 байт ID и 32 байта секрета.
3. Сохранить hash, поля и TTL.
4. Добавить ID в множество сервиса.
5. Вернуть полный токен один раз.
6. Записать аудит `token.create` без секрета.

Отзыв:

1. Удалить ключ токена и ID из множества.
2. Записать аудит `token.revoke`.

## 6. Матрица прав

| Операция | read | write | admin | cookie admin |
|---|---|---|---|---|
| `GET /api/users`, карточка без ссылок | да | да | да | да |
| `GET /api/summary`, трафик, таймлайн | да | да | да | да |
| Создание, импорт, лимиты, блокировка | нет | да | да | да |
| Перевыпуск секрета, QR, ссылки, история | нет | да | да | да |
| Квоты, риск, заметки, доверенные адреса | нет | да | да | да |
| `GET/PUT /api/settings*` | нет | нет | да | да |
| `GET /api/admins`, управление админами | нет | нет | да | да |
| `GET /api/audit`, `/api/audit.csv` | нет | нет | да | да |
| `GET /api/diagnostics` | нет | нет | да | да |
| Сервисные аккаунты и токены | нет | нет | нет | да |

`apiMe` для сервиса возвращает имя `service:<name>`, вычисленную роль,
пустой CSRF и scope. UI этот ответ для сервисов не использует, но
контракт остаётся предсказуемым.

## 7. API управления

Все маршруты требуют cookie-сессию администратора и CSRF.

### `GET /api/services`

Возвращает массив:

```json
[
  {
    "name": "monitoring",
    "description": "Prometheus exporter",
    "scope": "read",
    "disabled": false,
    "tokens": 2,
    "createdAt": "2026-11-26T10:00:00Z",
    "updatedAt": "2026-11-26T10:00:00Z",
    "createdBy": "admin"
  }
]
```

### `POST /api/services`

Тело:

```json
{"name":"monitoring","description":"Prometheus exporter","scope":"read"}
```

Ответ `201` с представлением сервиса. Ошибки: `400 bad_request` для
валидации, `409 conflict` для существующего имени.

### `PATCH /api/services/{name}`

Тело с любыми из полей:

```json
{"description":"...","scope":"write","disabled":true}
```

Ответ `200` с представлением. Смена scope действует на все токены сразу.

### `DELETE /api/services/{name}`

Тело:

```json
{"confirm":"monitoring"}
```

Ответ `204`. Неверное подтверждение — `400 bad_request`.

### `GET /api/services/{name}/tokens`

Возвращает массив:

```json
[
  {
    "id": "0123456789abcdef",
    "label": "ci",
    "prefix": "tgadm_0123456789abcdef",
    "createdAt": "2026-11-26T10:00:00Z",
    "createdBy": "admin",
    "expiresAt": "2027-02-24T10:00:00Z",
    "lastUsedAt": "2026-11-26T12:00:00Z"
  }
]
```

`expiresAt` и `lastUsedAt` могут отсутствовать. Секрет не возвращается.

### `POST /api/services/{name}/tokens`

Тело:

```json
{"label":"ci","expiresInDays":90}
```

`expiresInDays=0` — бессрочный. Если поле не передано, срок — 90 дней.
Ответ `201`:

```json
{
  "id": "0123456789abcdef",
  "token": "tgadm_0123456789abcdef_...",
  "label": "ci",
  "prefix": "tgadm_0123456789abcdef",
  "createdAt": "2026-11-26T10:00:00Z",
  "expiresAt": "2027-02-24T10:00:00Z"
}
```

Поле `token` возвращается только в этом ответе.

### `DELETE /api/services/{name}/tokens/{id}`

Ответ `204`. Неизвестный ID — `404 not_found`.

### Ошибки

- `400 bad_request` — неверные поля, срок, подтверждение.
- `401 invalid_token` — неверный или истёкший Bearer-токен.
- `403 forbidden` — scope не позволяет операцию.
- `403 session_required` — управление сервисами или токенами по токену.
- `404 not_found` — нет сервиса или токена.
- `409 conflict` — имя сервиса занято.
- `429 too_many` — превышен лимит сервисов или токенов.

## 8. Интерфейс

Маршрут `/services`, пункт меню «Сервисные аккаунты» только для admin.

Страница:

- заголовок и кнопка «Создать сервис»;
- таблица: имя, описание, scope, токенов, статус, создан, действия;
- пустое состояние с объяснением, зачем нужны сервисные аккаунты;
- мобильная карточная раскладка, как на других страницах.

Диалог создания и редактирования:

- имя (только при создании, потом неизменяемо);
- описание;
- scope с пояснением: «Чтение», «Клиенты», «Администратор»;
- при редактировании — переключатель «Отключён»;
- предупреждение, что смена scope действует на все токены.

Диалог токенов:

- таблица: метка, публичный ID, создан, срок, последнее использование;
- кнопка «Выпустить токен»;
- форма выпуска: метка и срок (бессрочно или число дней, по умолчанию
  90);
- после выпуска — отдельный экран с полным токеном, кнопкой
  «Скопировать» и предупреждением «токен показывается один раз»;
- отзыв с подтверждением;
- отключённый сервис показывает предупреждение, что токены не работают.

Удаление сервиса — диалог с вводом имени и предупреждением об удалении
всех токенов.

## 9. Аудит и наблюдаемость

События:

- `service.create` — target имя, result scope;
- `service.update` — target имя, result `scope=<old>-><new> disabled=<old>-><new>`;
- `service.delete` — target имя, result ok;
- `token.create` — target `<service>/<id>`, result label и срок;
- `token.revoke` — target `<service>/<id>`, result ok.

Секрет токена и его хеш в аудит и вебхуки не попадают.
`last_used_at` обновляется без аудита, чтобы не создавать событие на
каждый запрос.

Метрики Prometheus не добавляются в этой версии: аудита и `last_used_at`
достаточно для эксплуатации. Если понадобится, счётчик запросов по
scope можно добавить отдельно.

## 10. Безопасность

- Полный токен существует только в ответе на выпуск и в памяти клиента.
- В Valkey хранится SHA-256 секрета, не сам секрет.
- Сравнение хеша — `crypto/subtle.ConstantTimeCompare`.
- Ошибка аутентификации не различает причину.
- Ответы с токеном и списками идут с `Cache-Control: no-store`.
- `Authorization` не логируется: журнал запросов пишет метод, путь,
  статус, время и IP, но не заголовки.
- Bearer-запросы не проходят CSRF, потому что не используют ambient
  cookie; allowlist по CIDR остаётся.
- Управление сервисами и токенами недоступно по токену.
- Отключение сервиса и отзыв токена действуют немедленно.
- Секреты не попадают в вебхуки и экспорт аудита.

## 11. Совместимость и миграция

- Новые ключи: `auth:services`, `auth:service:*`,
  `auth:service_tokens:*`, `auth:token:*`.
- Существующие ключи `auth:user:*`, `auth:session:*` не меняются.
- Новых переменных окружения нет.
- Откат на 1.8.0 безопасен: старый код новые ключи игнорирует, токены
  перестают работать.
- Обновление не требует миграции данных.

## 12. Тестирование

### Store

- создание, чтение, список, изменение и удаление сервиса;
- конфликт имени;
- лимит 50 сервисов;
- выпуск токена, хранение хеша, проверка секрета;
- лимит 20 токенов;
- истечение срочного токена;
- отключение сервиса блокирует проверку токена;
- отзыв удаляет ключ и индекс;
- удаление сервиса удаляет все токены;
- обновление `last_used_at` не чаще раза в минуту.

### Auth и web

- валидный токен read/write/admin;
- неверный формат, неизвестный ID, неверный секрет, истёкший токен,
  отключённый сервис;
- read не мутирует и не видит ссылки;
- write управляет клиентами, но получает 403 на настройках, админах,
  аудите, диагностике, сервисах и токенах;
- admin проходит админские маршруты, но получает 403 на управлении
  сервисами и токенами;
- cookie-сессия работает как раньше;
- Bearer имеет приоритет над cookie;
- CSRF не требуется для Bearer и требуется для cookie;
- аудит actor `service:<name>`;
- создание, изменение, удаление сервиса и выпуск/отзыв токена;
- подтверждение удаления;
- токен показывается только в ответе на выпуск.

### Frontend

- страница списка и пустое состояние;
- создание и редактирование;
- отключение и удаление;
- диалог токенов, выпуск, одноразовый показ, копирование, отзыв;
- ошибки API;
- мобильная раскладка.

### E2E

1. Администратор создаёт сервис `read`.
2. Выпускает токен и копирует его.
3. Вызывает `GET /api/users` с Bearer и получает список.
4. Пытается создать клиента и получает 403.
5. Администратор меняет scope на `write`.
6. Тот же токен создаёт клиента.
7. Отзыв токена возвращает 401.

Пороги покрытия сохраняются: API 85%, UI 85% строк, инструкций и
функций, 70% ветвей.
