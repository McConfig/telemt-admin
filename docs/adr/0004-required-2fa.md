# ADR-0004: обязательная 2FA с льготным сроком

- Статус: принято
- Дата: 2026-11-25
- Контекст: версия 1.5.0

## Проблема

2FA доступна, но не обязательна. Администратор может годами работать без
второго фактора. Полностью блокировать вход в день включения требования
нельзя: единственный администратор потеряет доступ и не сможет включить
2FA.

## Решение

1. Две активные настройки: `security.require_2fa` и
   `security.require_2fa_grace_days` (0–30, по умолчанию 7).
2. При включении фиксируется `security:require_2fa_since`. Дедлайн =
   момент включения + льготные дни. Изменение срока пересчитывает дедлайн;
   выключение удаляет отметку.
3. Администратор без 2FA видит в интерфейсе предупреждение с числом
   оставшихся дней.
4. После дедлайна вход по паролю остаётся возможным, но все API, кроме
   `/api/me`, выхода, смены пароля, сессий и настройки TOTP, отвечают
   `403 totp_required`. Интерфейс показывает экран настройки 2FA.
5. После включения 2FA ограничение снимается автоматически.
6. Администратор не может отключить 2FA, пока требование активно.
7. Обычные пользователи с ролью `viewer` не затрагиваются.

## Альтернативы

1. **Полная блокировка входа после дедлайна.** Единственный админ
   блокирует сам себя; нужен CLI или второй админ. Отклонено.
2. **Только предупреждение без ограничения.** Не решает задачу.
3. **Индивидуальные сроки на пользователя.** Гибче, но сложнее; глобального
   срока достаточно для малого проекта.
4. **Отдельный экран настройки 2FA без доступа к остальному UI.** Реализован
   как ограничение API и принудительный экран аккаунта.

## Последствия

- Новый ключ `security:require_2fa_since`, миграция не нужна.
- Требование действует только на администраторов; viewer может работать
  без 2FA.
- Если администратор потерял телефон, другой администратор с 2FA может
  сбросить его TOTP; после сброса доступ снова ограничится до настройки.
- При включении через env срок начинается при старте приложения.
- Откат на версию без этой функции безопасен: ключ игнорируется.
