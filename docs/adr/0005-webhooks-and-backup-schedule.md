# ADR-0005: вебхуки и расписание бэкапов

- Статус: принято
- Дата: 2026-11-26
- Контекст: версия 1.5.0

## Проблема

Внешним системам нужно узнавать о событиях без опроса API. Оператору нужно
менять время и срок хранения бэкапов без SSH и правки systemd.

## Решение

### Вебхуки

1. Настройки `notifications.webhook_url`, `webhook_secret`, `events`
   активны; секрет не возвращается API.
2. Событие — действие аудита. Список задаётся именами, `*` включает всё.
3. Отправка асинхронная: очередь 128, три попытки с задержками 1, 5 и 15
   секунд, таймаут 10 секунд.
4. Подпись HMAC-SHA256 от `<timestamp>.<body>` в
   `X-TeleMT-Signature`. Дополнительно `X-TeleMT-Event`,
   `X-TeleMT-Delivery`, `X-TeleMT-Timestamp`.
5. Кнопка «Проверить вебхук» отправляет событие `test` без фильтра.
6. Доставка не персистентна: при перезапуске очередь теряется.

### Расписание бэкапов

1. Настройки `backup.schedule`, `keep_days`, `restore_test` активны.
2. Приложение атомарно пишет JSON в `TGADMIN_BACKUP_CONFIG`.
3. Хостовый скрипт запускается каждые 5 минут, читает JSON и делает снимок
   только в указанное время, один раз в сутки. После успеха пишет
   `TGADMIN_BACKUP_STATUS`.
4. Приложение не запускает systemd и не копирует RDB: это остаётся на
   хосте. Без смонтированного каталога настройки сохраняются в Valkey, но
   не применяются.
5. Ручной снимок из панели по-прежнему делает `BGSAVE` в Valkey.

## Альтернативы

1. **Персистентная очередь вебхуков в Valkey.** Надёжнее, но сложнее;
   отложено.
2. **Приложение само делает бэкапы.** Нужен общий том с Valkey и
   восстановление контейнера; выходит за границы приложения.
3. **Прямая правка systemd из UI.** Требует привилегий и опасна.
4. **Опрос API вместо вебхуков.** Дороже для внешних систем и не даёт
   событий в реальном времени.

## Последствия

- Новые ключи `settings:global` только; миграции нет.
- Секрет вебхука хранится в Valkey и не показывается в API.
- Хостовый скрипт должен поддерживать чтение JSON и запуск каждые 5 минут.
- При недоступном получателе события теряются после трёх попыток; это
  видно в логах.
- Изменение расписания не требует перезапуска приложения, только
  следующего запуска таймера.
