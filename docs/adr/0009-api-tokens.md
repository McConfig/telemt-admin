# ADR-0009: сервисные аккаунты и API-токены

- Статус: принято
- Дата: 2026-11-26
- Контекст: версия 1.9.0

## Проблема

Внешним скриптам и мониторингу нужен доступ к API без пароля
администратора, cookie-сессии и CSRF. Пароль даёт полный доступ человека,
не отзывается отдельно и завершает все сессии при смене. Нужны машинные
учётки, ограниченные права, срок жизни и аудит.

## Решение

1. Ввести сервисные аккаунты — машинные учётки без пароля, отдельно от
   пользователей UI. Управление только из cookie-сессии администратора.
2. Ограничить права тремя scope: `read` (как viewer), `write`
   (управление клиентами), `admin` (всё, кроме управления сервисами,
   токенами и `/api/account*`).
3. Приводить cookie-сессию и Bearer-токен к единому principal в
   существующем middleware. Это сохраняет один набор API-контрактов.
4. Формат токена `tgadm_<id>_<secret>`, в Valkey хранить только SHA-256
   секрета. Полный токен показывать один раз.
5. Поддержать несколько токенов на сервис, срок 1–3650 дней или
   бессрочно, отзыв и отключение сервиса.
6. Не разрешать токену управлять сервисами и токенами: утёкший токен не
   должен размножать доступ.
7. Писать аудит `service.*` и `token.*`; не аудировать каждый запрос,
   обновлять `last_used_at` не чаще раза в минуту.

## Альтернативы

1. **Отдельный роутер `/api/service/...`.** Изоляция, но дублирование
   всех эндпоинтов и неизбежное расхождение контрактов.
2. **Скрытые пользователи UI для сервисов.** Переиспользует роли, но
   ломает смысл пользователей, паролей и списка админов.
3. **JWT.** Не требует хранения, но усложняет мгновенный отзыв и
   ротацию; для одного приложения Valkey проще.
4. **Точные scopes на каждый ресурс.** Гибко, но сложно проверять и
   объяснять; трёх уровней достаточно для текущих задач.
5. **Бессрочные токены только.** Удобно, но повышает ущерб от утечки;
   бессрочность оставлена опцией, по умолчанию 90 дней.

## Последствия

- Новые ключи `auth:services`, `auth:service:*`,
  `auth:service_tokens:*`, `auth:token:*`; миграции нет.
- Откат на 1.8.0 безопасен: старый код новые ключи игнорирует, токены
  перестают работать.
- Bearer-запросы не проходят CSRF, но остаются в allowlist по CIDR.
- Смена scope сервиса действует на все его токены сразу.
- Управление токенами недоступно по токену; это осознанное ограничение.
- Секреты не попадают в списки, аудит, вебхуки и логи.
