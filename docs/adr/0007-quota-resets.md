# ADR-0007: массовый и плановый сброс квот

- Статус: принято
- Дата: 2026-11-26
- Контекст: версия 1.7.0

## Проблема

Сброс квоты был доступен только в карточке одного клиента. При сотнях
клиентов оператор нажимал кнопку в каждой карточке, а периодический сброс
приходилось делать вручную или внешним cron-скриптом. Внешний скрипт не
знал о ручных сбросах, не писал аудит и мог сбросить квоту дважды.

## Решение

1. Добавить `POST /api/users/reset-quota`: массовый сброс выбранных
   клиентов или всех. Тело `{"names":[...]}` необязательно; пустой список
   означает всех. Ограничение — 1000 имён за запрос.
2. Обрабатывать имена последовательно в одном запросе и возвращать отчёт:
   `total`, `reset`, `refused`, `unknown`, `notSent` и список `failed` с
   причиной по каждому клиенту.
3. Хранить переопределение расписания на клиента в Valkey (`quota:reset:<name>`):
   `inherit`, `off` или `custom` с `days` и `time`. Глобальные значения —
   настройки `quota.reset_enabled`, `quota.reset_days`, `quota.reset_time`.
4. Запускать планировщик в процессе tgadmin раз в 30 секунд. Он читает
   список клиентов, вычисляет действующее расписание и сравнивает время
   последнего запуска (`quota:last:<name>`) с текущим.
5. Первый проход только задаёт точку отсчёта: квота не сбрасывается сразу
   после включения расписания. Если приложение было выключено несколько
   интервалов, выполняется один сброс, а не серия пропущенных.
6. После ручного сброса обновлять точку отсчёта, чтобы планировщик не
   повторил сброс через несколько секунд.
7. Защищать сброс клиента блокировкой `quota:lock:<name>` на 30 секунд:
   ручной и плановый сброс не выполняются одновременно, массовый сброс
   помечает занятого клиента как `refused`.
8. Писать аудит: `user.reset_quota` для ручного сброса,
   `quota.reset.bulk` с итогами для массового и
   `quota.reset.scheduled` для каждого планового сброса.

## Альтернативы

1. **cron на хосте.** Не знает о ручных сбросах, не имеет доступа к
   настройкам и аудиту, требует отдельного секрета.
2. **Сброс внутри telemt по расписанию.** Управление расписанием
   переехало бы в telemt, а интерфейс потерял бы единое место настроек.
3. **Асинхронная очередь с прогрессом.** Для 1000 клиентов локального
   Control API синхронный запрос укладывается в секунды; очередь усложняет
   хранение состояния и восстановление после перезапуска.
4. **Cron-выражения на клиента.** Гибко, но избыточно для одной операции
   и повышает риск ошибки ввода.

## Последствия

- Автосброс по умолчанию выключен: обновление не меняет поведение
  существующих установок.
- Первый сброс происходит не раньше чем через `days` дней после включения
  расписания или после первого запуска планировщика.
- Время трактуется в часовом поясе процесса (`TZ` контейнера), минуты
  кратны 5.
- Массовый сброс синхронный; при недоступном Control API запрос всё равно
  вернёт отчёт по уже обработанным клиентам.
- Блокировки живут в Valkey, поэтому несколько экземпляров tgadmin не
  сбросят одного клиента одновременно.
